## 1. The problem, per channel

**RB-1 — Authorization-store restore resurrects revoked permission.** The authorization store (`scripts/settlement-evidence-authorization-store.js`, PR #706) is append-only and decides from exactly one read-only statement over its own three relations (`auth_eligibility`, `auth_revocation`, `auth_session_revocation`; the read returns the eligibility record plus `operation_revoked` / `session_revoked` facts). Its header states the gap plainly: there is no external reference value to compare against, so a self-consistent older state is indistinguishable from current state by construction. Restore the database/schema to a pre-revocation checkpoint, restart the deciding process, and the final decision authorizes against the stale state with no signal anything regressed (MP-14 / INT-G1, reproduced). INT-4's RQ-5 is the same channel stated for `auth_session_revocation` (OD-2 logout revocations).

**RB-2 — Terminal-history snapshot rollback across restart.** The only rollback check in shipped code is in `scripts/settlement-evidence-terminal-certificate.js`: `qualifySnapshot` keeps a floor in a module-level `checkpoints` **WeakMap** (line 20) — a snapshot below the floor revision *this process has already qualified*, or whose prefix digest diverges from it, throws `terminal rollback`. The WeakMap is empty in a fresh process, so after a restart a rolled-back but self-consistent history+checkpoint pair qualifies cleanly. The PostgreSQL adapter (`settlement-evidence-postgres-adapter.js`, native-history profile with the `terminal_history` relation) implements `readSnapshot()` / `compareAndAppend()` over byte rows and calls `qualifySnapshot` on every read and append — every one of those calls trusts a floor that evaporates on restart. There is no durable or external anchor and no `epoch` concept anywhere in the settlement code.

**RB-3 — Maintenance restore with stale anchors installs the older state silently.** The shipped restore path (`scripts/settlement-evidence-restore-install.js`, PR #712) validates a candidate byte-exactly against **operator-supplied** anchors — `anchors.ledger = { revision, documentDigest }` and `anchors.history = { schema, householdId, ledgerNamespace, revision, digest }` — quarantines incumbents in one transaction, and installs. Its own non-claims state that anchor provenance/latestness are *trusted maintenance input*, and it never calls `TC.qualifySnapshot` or `TC.registerDomain`. If the supplied anchors describe an older state, the install faithfully installs the older state and `verifyRestoreInstall` — same trusted anchors over the readback bytes, plus agreement with an independently supplied pin — confirms it. Latestness is trusted, never proven. (The pin it checks against is only as good as the pin store behind it — which today is an injected surface with no named production implementation: checklist C-6, OPEN.)

The common shape: **every store that matters is self-referential.** Each can prove internal consistency; none can prove *latestness* against a value held outside its own restorable unit. The mechanism below adds exactly that external reference, in one custody unit, for all three channels.

## 2. The proposed mechanism

### 2.1 One anchor unit, three records

A single **anchor unit** — a small store outside the backup/restore boundary of both the financial evidence store and the authorization store — holds three monotone records:

| Record | Keyed by | Contents | Advances when |
|---|---|---|---|
| **Financial pin** (already designed, unnamed in production) | household | `{ revision, digest, timestamp }` — the exact shape `settlement-evidence-store.js` validates on every read (`validPinRecord`) — carried in an anchor record that also binds the unit **incarnation** (§2.1.1), which the pin payload itself does not carry | The store's existing flows: genesis (`pinStore.advance(null, {revision: 0, …})`) and promotion (archive head → readback verify → fresh pin re-read → `pinStore.advance(expected, next)`). **No change to the store.** This design names the production implementation of the already-injected `pinStore.read/advance` surface (checklist C-6). |
| **Authorization anchor** (new) | scope | `{ scope, incarnation, epoch, revocationCount, frontierDigest, lastEventId, updatedAt }` | Every revocation append (operation or session) committed by the authorization store — under the protocol in §2.3.2. |
| **History anchor** (new) | (householdId, ledgerNamespace) domain | `{ incarnation, revision, digest, lastEventId, updatedAt }` — the priming payload is the terminal-history checkpoint pair `(revision, digest)` that `qualifySnapshot` already trusts in-process; the record additionally binds the unit incarnation and the advancing event (revision 3 — required by the pending-event proof, §2.4.2) | Every successful `compareAndAppend` in the PostgreSQL adapter, after COMMIT — under the pending-event protocol in §2.4.2. |

Every record advance is a **compare-and-swap**: `advance(expected, next)` resolves the literal `true` only for an acknowledgement-verified conditional write, the literal `false` only for a definite conflict, and throws otherwise — the exact semantics the shipped object adapter already specifies for `pinStore.advance` (`settlement-evidence-object-adapter.js` header), including its transition validation: genesis against an absent record, or a sequential advance only — **no rollback, no same-revision different-digest fork, no skipped revision**. An anchor record can therefore never be moved backward by its own write path; moving it backward requires restoring the anchor unit itself, which is the adversary-independence question (§2.2, §2.8, Q-C) and is **unproven** until demonstrated.

Alongside the three records, the anchor unit keeps an **append-only provenance log** of create-only entries (intents, acks, voids — §2.3.2). This is the per-anchor provenance record checklist C-5 requires (source, read time, hash) — produced by the mechanism itself, not reconstructed afterwards. Whether every advance in fact carries complete provenance is a property the protocol is designed to make auditable and the S1/S8 suites must prove; it is not asserted as established (§0 of revision 2, finding D). One consequence the reconciliation protocol (§2.3.3) relies on: because every advance is driven by exactly one recorded intent whose entry bytes are a deterministic function of the intent (§2.1.1, §2.3.2), the **anchored revocation set is reconstructible** — primarily by **generation-chain replay** (§2.3.3, Phase L): the retained generations, replayed in order from genesis, accumulate exactly the set each generation certified, and the replay is verified against the anchor record's `frontierDigest` before the set is used. The older reconstruction — genesis (the empty set) plus the entries of all **acked** intents — is retained only as an audit cross-check (every ack must be replay-consumed; revision 4): it is **not** the gate, because an advance whose ack was lost is landed history, not a mismatch — Atlas's revision-3 trace 1 defeated exactly the acked-intent reconstruction used as a gate. The record itself therefore does not need to embed the set; the chain carries it, and a chain that cannot reproduce the record's digest is unproven by definition.

#### 2.1.1 Canonical encoding, domain binding, epoch/incarnation semantics (decision 2)

The authorization frontier is a digest over the scope's complete revocation set. For that digest to bind anything, its preimage encoding must be injective and domain-bound. The design fixes it as follows (S2 implements exactly this; any change is a new encoding version, never a silent edit):

- **Frame.** `frame(x) = u32be(len(x)) || x` for byte strings; integers are fixed-width `u64be`. Text fields are the validated store literals (scope/schema per the store's construction regexes; operation/generation per theirs) encoded as UTF-8 bytes. Digest fields held by the store as lowercase hex (`HASH_RE`-validated) are encoded as the **raw 32 bytes** decoded from hex, so case or representation can never alias.
- **Entry encodings (type-tagged).** Operation revocation: `frame("oprev") || frame(operationId) || frame(generation) || u64be(revokedAt)`. Session revocation: `frame("sesrev") || frame(rawBytes(sidDigest)) || u64be(revokedAt)`. The tag is part of the preimage: an operation revocation and a session revocation can never encode to the same bytes, and no field boundary is ambiguous because every variable-length field is length-framed.
- **Set encoding.** Entries are sorted lexicographically by their full encoded bytes (deterministic, independent of insertion order — the shipped relations carry no sequence column, §7, so insertion order is not available and is never relied on). Preimage: `frame("atlas-auth-frontier") || frame(encodingVersion) || frame(schema) || frame(scope) || frame(incarnation) || u64be(count) || entries…`. `frontierDigest = SHA-256(preimage)`.
- **Domain binding.** Schema and scope are inside the preimage: two stores differing in either can never produce an equal frontier. The **incarnation** (below) is also inside the preimage, so a frontier from a re-created anchor lineage can never equal one from the original lineage even over an identical revocation set.
- **Epoch.** The anchor record's `epoch` is the count of anchor advances since genesis for that (scope, incarnation) — the record's version. Epoch is carried in the record, not the digest preimage (the digest identifies the *set*; the epoch identifies the *record generation*). An anchor read showing a lower epoch than a value previously observed for the same incarnation is an anchor regression: unverifiable, refusal (§2.6).
- **Incarnation.** At genesis (§2.6) the anchor lineage for a scope is created with an `incarnation` value: the digest of the genesis event (genesis provenance entry: scope, schema, genesis frontier — the empty set — and a genesis nonce from the provisioning procedure). The incarnation is constant across every advance of that lineage, is embedded in every record and every frontier preimage, and changes **only** at a re-genesis. Consumers compare incarnation as part of equality: a record from a different incarnation never compares equal to the expected lineage, whether or not the intermediate absence was ever observed. **Where a consumer learns the expected incarnation — revised in revision 3 (blocker 3).** Revision 2 sourced the expectation from the anchor unit's own provenance chain; that is self-referential — a restored unit presents an older chain that is internally consistent, and an admin restore need not pass through a compliant re-genesis — and the claim is **withdrawn**. The expectation now comes from outside the anchor unit, per record: for the **authorization anchor**, from the cross-witness high-watermark in the authorization database's restore domain (§2.3.5), bound when a composer opens the scope and re-checked at every reconciliation; for the **history anchor and the financial pin**, there is **no independent incarnation base, and revision 4 narrows the claim to match**: the pin payload `{ revision, digest, timestamp }` does not carry an incarnation at all (§2.1), and neither record's `(revision, digest)` pair can prove one — agreement between the pair and the head the terminal-history relation / the financial store presents (§2.4, §2.5) proves only that the pair *describes that head*, never which anchor lineage issued it, so a recreated anchor unit faithfully copying the current pair is indistinguishable by the pair alone, and a pair the data unit contradicts is unverifiable on its face. Data-head agreement is a **staleness/divergence check** for these two records, **not** an incarnation check; their incarnation continuity is **UNPROVEN** (with Q-C, §3) and rests on the §2.8 principal restrictions and the ceremony, not on the pair; at restore/qualification ceremonies, from the owner-held notarization **if adopted** (§2.2, Candidate C as complement) as an additional check, never the sole one. A presented incarnation for which no independent comparison base is available in the consumer's context is **unverifiable** — the consumer refuses — not self-evidently valid.

Eligibility rows remain **excluded** from the frontier, per the v1 reasoning Atlas accepted as directionally suitable: the store is append-only for eligibility too, so a rollback can only *remove* eligibility, while resurrection of a *revoked permission* requires a revocation to disappear, which is exactly what the frontier measures. §2.1.2 proves the exclusion cannot be undermined by the store's own flows **for the revocation threat**. One qualification, added in revision 3 (blocker 6): removal alone is fail-safe for admission (no record, no admission), but removal followed by a differing re-issuance swaps the record's bindings under an unchanged frontier — the frontier does not and cannot bind eligibility, so that case is answered at the joint-decision seam (§2.1.2, §2.3.1 rule 4), not here. (If a future slice makes eligibility mutable, the frontier definition must be revisited; recorded here so the exclusion is a decision, not an oversight.)

#### 2.1.2 Why removal/reissuance cannot undermine the revocation bindings — and what it does not prove (decision 2, narrowed by blocker 6)

Claim (**narrowed in revision 3**): no sequence of the authorization store's own operations can return the frontier to a previously anchored (count, digest) while the **revocation facts** for any key differ from what they were when that frontier was anchored; and no operation can remove or alter a revocation. The claim is about revocation membership only. It is **not** a claim about decision facts in general — eligibility facts are expressly outside it (see the eligibility paragraph below). Grounded in the shipped module (re-read at `aacd44c2`, §7):

1. **The store's statement set contains no UPDATE or DELETE.** Its frozen SQL is INSERT/SELECT only, and its relation contract grants are `SELECT, INSERT` on all three relations (the connection preflight additionally *forbids* UPDATE/DELETE/TRUNCATE at provisioning). Removal of a revocation row is therefore impossible through the module; it is possible only through the external restore that is the RB-1 adversary — which is precisely what the anchor detects.
2. **Reissuance cannot mutate.** `issueEligibility` compares the stored record inside the transaction: an identical reissue resolves `reissued-identical` with no write; any differing immutable field is a definite conflict refusal after an affirmed ROLLBACK. The stored record is never overwritten, and no statement carries an ON CONFLICT clause. Reissuance also touches only the eligibility relation — it cannot add, remove, or alter a revocation row in either revocation relation.
3. **Revocation appends are idempotent and non-overwriting.** An existing key resolves `already-present` (ending in ROLLBACK, no write — the stored `revoked_at` is never replaced); a new key is a single INSERT whose durable success is reported only after an affirmative COMMIT tag.
4. **Consequence for the frontier.** Through the module's flows the revocation set grows monotonically by set inclusion. The canonical encoding (§2.1.1) is injective over sets (type-tagged, length-framed, sorted, domain-bound), so (count, digest) changes **iff** the set changes, up to SHA-256 collision resistance. A strict-subset restore therefore yields a different frontier (lower count, or — if legitimate appends intervened — a different digest), and equality-or-refuse (§2.3.1) refuses. A decision for a revoked (operationId, generation) key reads `operation_revoked` from the *same snapshot* as the frontier (§2.3.1), so a later reissuance of a *different generation* — a distinct key with its own eligibility semantics under the B4 design — cannot retroactively alter the revoked key's facts or its frontier binding.

**What this does not prove — eligibility (blocker 6).** Eligibility rows are excluded from the frontier (§2.1.1), so the frontier is **unchanged by issuance**: ordinary issuance of a new key changes the decision facts for that key with (count, digest) exactly as before, by design. Worse, the conflict check in point 2 fires only against an **existing** row — verified in the shipped `issueEligibility`, which compares the stored record only when its keyed SELECT returns one row and otherwise inserts. A rollback that removes an eligibility row therefore disarms the check: a subsequent same-key issuance with differing `householdId`/`confirmationDigest`/`secretDigest`/`issuedAt` is a fresh INSERT, and no frontier comparison can see it. This design does **not** claim the frontier binds eligibility, and does not extend the frontier to cover it (eligibility churn would anchor every issuance and still could not bind a *presented* proof to a record). The binding is instead established at the only place it can be — the joint-decision seam — as §2.3.1 rule 4: the decision verifies, against the same combined-snapshot result it already requires, the record's key (structural), its `householdId`, and that the attempt's presented confirmation and secret proofs digest-match the record's `confirmationDigest` and `secretDigest`. After a rollback-and-reissue under different digests, every presentation derived from the original issuance fails rule 4; a re-issuance carrying the original `householdId` and both original digests matches the original record on **every field rule 4 binds** (key, householdId, confirmationDigest, secretDigest) and is therefore equally bound, hence harmless — the record as a whole is **not** claimed byte-identical (narrowed in revision 4): fields the seam does not bind, `issuedAt` among them, may differ without affecting any decision the seam protects. A record swapped *after* the snapshot is a different attempt's problem: it is read by that attempt's own statement and refused there.

What this proof does **not** cover, stated plainly: a principal who can write the database outside the module (the restore adversary) — detection, not prevention, is the anchor's job; and SHA-256 collision attacks — out of scope for this threat model, as everywhere else in the codebase.

### 2.2 Where the anchor lives — candidates compared (status per decision 1)

The requirement (INT-4 RQ-7): the anchor must live in an **independently restorable unit** — an anchor stored inside the same restorable unit as the store satisfies nothing. The rollback adversary is INT-4's: an operator/restore path that can roll back the store (provider backup/restore, snapshot replacement, or the shipped maintenance restore) must not be able to roll back the anchor with it.

**Atlas's disposition (decision 1): Candidate B is a reasonable candidate for revision; Candidate A is retained as an alternative; NEITHER is adopted or provider-qualified by the review.** The text below is revised to that status: B is this design's *candidate*, and the independence arguments for both are claims whose proof obligations are listed in §3 (Q-C) — a different provider or project boundary is a candidate boundary, **not** RQ-7 proof (finding C).

**Candidate A — A separate Neon database (distinct project) with a dedicated anchor role.**
One small schema (three record rows + provenance table), written through a dedicated session under the same discipline the authorization connection already enforces (CONNECTION LIMIT 1, least-privilege grants, PG18 preflight shape). CAS is a single-row conditional `UPDATE … WHERE epoch = $expected` with the rowCount discipline the adapter's `compareAndAppend` already uses.
*Independence claim (unproven):* a distinct Neon project is a distinct backup/PITR domain — restoring the store's project does not touch it, and vice versa. But it is the **same provider and the same class of tooling** as the store: the Q-C demonstration must argue project-level separation, and an operator holding both projects' credentials holds both units. The anchor role's credentials must therefore be distinct from every store role, and anchor-unit restores must be treated as qualification-invalidating events (§2.6).

**Candidate B — Object storage with generation preconditions (the design's candidate).**
The anchor records live as small objects in a dedicated bucket/prefix; an advance is a conditional write bound to the object's current generation (`ifGenerationMatch`-style precondition), and the provenance log is a chain of create-only objects. This is not a new invention for this codebase: the object adapter's transport contract already *requires* real compare-and-swap — "compare-and-swap is never emulated with an unconditional write" — with version-bound conditional writes and atomic absent-only creates, and the repo ships a GCS generation transport (PR #703). The anchor store is a new small module over that documented contract.
*Independence claim (unproven):* the anchor's restore boundary is a different provider system from every PostgreSQL backup/restore path in the adversary model; no PG restore, snapshot replacement, or maintenance install touches it, and generation preconditions make a stale writer's conditional write fail as a definite conflict. What generation CAS does **not** do — fresh-token overwrite or delete/recreate by a sufficiently privileged principal — is finding C, answered by the principal/incarnation model in §2.8 and §2.1.1, and remains a proof obligation, not a property this document asserts.
*Costs, stated honestly:* an extra network dependency on the decision path (an anchor outage fails decisions closed — §2.6); bucket versioning/lifecycle must be configured so a read always names the live generation (a provisioning requirement, recorded in §6 as Dale's); whether the shipped #703 GCS transport satisfies the object adapter's transport contract unchanged is a build-slice verification item, **not** assumed here.

**Candidate C — An owner-held offline record.**
A digest the owner keeps outside all provider systems (device, password manager, paper), updated at checkpoints.
*Independence:* total — no provider restore reaches it. But the write events are frequent (every revocation, every terminal append); a human-in-the-loop record cannot advance on every event, and if decisions must wait for it, the owner becomes an availability single point of failure (RQ-6 fails in practice). As the *sole* anchor it fails Q-B. As a **complement** — a periodic notarization of the online anchor's head digests, checked at restore ceremonies and used to pin the expected incarnation (§2.1.1) — it adds genuine defence in depth and is recommended in that limited role only (adoption is Dale's decision, §6).

**Candidate statement:** Candidate B, because its latestness proof rests on a provider-enforced generation match rather than on separation-by-convention, and because it reuses the codebase's already-reviewed CAS contract and transport instead of inventing a new one. Candidate A remains an acceptable alternative if the decision desk prefers database-only custody; its CAS is equally sound, but it shares the store's provider and restore tooling class, which weakens the Q-C demonstration. Neither candidate is adopted by this document; the provisioning/spend/credential choices inside either belong to Dale (§6) — this design proposes the mechanism class, it does not provision anything.

### 2.3 Authorization anchor — snapshot, decision, and advance protocols (RB-1 / RQ-1, RQ-5)

Revision 1 specified the decision check as two reads — `readAuthorizationState`, then a separate frontier read compared to the anchor. Atlas's finding A defeats that algorithm with a reasoned trace, and the shipped source confirms the hole: the store serializes *units* on one queue (a whole transaction is one unit; the state read is one unit), but two reads are two units, and an append unit can land between them. This section replaces the algorithm.

#### 2.3.1 The decision check: one snapshot, and the linearization rule

*The combined read (S2).* The decision consumes **one statement execution** that returns, from a single statement snapshot: (a) the decision facts — exactly what the shipped `readState` returns today (eligibility record plus `operation_revoked` / `session_revoked` for the requested keys); and (b) the frontier — the revocation count and the canonical entry set (or an aggregate producing the §2.1.1 digest) over the scope's two revocation relations. Whether the digest is computed by the statement or by the caller over the rows that one statement returned is an S2 implementation choice; coherence comes from the single statement snapshot, not from where the hash runs. (A SQL-side digest would need a hash extension; none is assumed — §7.) The shipped `readState` is already one statement for the facts alone; S2 extends that statement, it does not add a second read. The combined read is one unit on the store's serial queue, so no append unit can interleave *inside* it.

*The anchor read — order is mandated (blocker 6).* Within an attempt, the anchor record is read **after** the combined statement executes, never before it. Revision 2 said only "in the same attempt"; that admits the pairing *anchor read → completed revocation → rollback → combined read*, where the statement (executing after the rollback) returns the pre-revocation frontier and facts, which then compare equal against the stale anchor read — pairing two stale states into a permissive decision on a revocation that *completed* before the statement ran. Under the mandated order that pairing cannot be produced: any revocation that completes before the statement is inside the statement's snapshot (rule 3 refuses on facts); any that completes between the statement and the anchor read moves the anchor (rule 2 refuses); a store rollback between them does not move the anchor, which is in a different unit (rule 2 refuses). The read returns (incarnation, epoch, count, frontierDigest), and the incarnation is compared against the lineage bound for this scope from the cross-witness (§2.3.5) — a record from a foreign lineage is unverifiable regardless of frontier equality.

**Linearization rule.** A decision attempt *linearizes at the execution of the combined statement*; the post-statement anchor read is a freshness gate on that linearization, not a second observation of the store. The attempt may proceed to the joint decision only if **all** of the following hold:
1. the combined statement resolves `ok` (the store's existing envelope discipline; anything else resolves unavailable);
2. the frontier **in that same result** equals the anchor record read after the statement in the same attempt — equality over (incarnation, count, frontierDigest), with the incarnation also matching the witness-bound lineage (§2.3.5);
3. the facts in that same result admit under the existing joint-decision rules;
4. **the seam bindings hold against that same result** (blocker 6): the returned eligibility record's key is the requested (operationId, generation) — structural in the shipped keyed read, whose row projection refuses a key-disagreeing row (§7); its `householdId` equals the attempt's session-resolved household; and the attempt's presented confirmation proof and browser-secret proof digest-match the record's `confirmationDigest` and `secretDigest` respectively. An absent record, or any mismatch, refuses. (§2.1.2 establishes why these bindings, and only these, answer rollback-and-reissue; the seam that evaluates them is the joint-decision integration the shipped store names as a later boundary — S4's, fixed by its fresh `server.js` read, §4/§7.)

The interleavings, exhaustively:

- *Revocation append + anchor advance complete before the statement:* the snapshot contains the revocation; rule 3 refuses on facts. (Dale's approved timing rule: a decision following a completed revocation must refuse.)
- *Revocation append commits, anchor advance has not completed, statement executes:* the snapshot frontier ≠ anchor (the set grew; the anchor still names the prior set) → rule 2 refuses; the attempt is retryable. Fail-closed, never permissive.
- *Statement executes, then a revocation append + advance complete before the decision is used:* the attempt linearized before the revocation completed; under the approved timing rule an admitted request may finish even if revocation completes afterward. The *next* attempt sees the revocation in its snapshot and refuses on facts.
- *Rollback removes an anchored revocation R1; statement executes after the rollback:* the snapshot frontier ≠ anchor → rule 2 refuses. This is the RB-1 case, closed.
- *Atlas's revision-1 trace — rollback removes R1, decision facts read, legitimate re-append restores R1, frontier then matches:* under the combined read there is no separate facts read and frontier query to interleave between. If the single statement executes while R1 is absent, its own frontier mismatches the anchor → rule 2 refuses (the decision never sees the permissive facts as usable). If it executes after the re-append, the facts in that same snapshot show R1 revoked → rule 3 refuses. Every placement of the statement in the trace refuses; the permissive outcome requires facts and frontier from *different* snapshots, which the protocol no longer produces.
- *Atlas's revision-2 trace (blocker 6) — anchor read, then a revocation completes, then the store rolls back, then the combined read:* excluded by construction. No attempt reads the anchor before its statement, so the stale-anchor/fresh-statement pairing the trace needs is never produced; in the mandated order, the statement (wherever it lands relative to the revocation and the rollback) is followed by an anchor read that reflects the completed revocation's advance — the anchor unit is not rolled back by a store rollback — and rule 2 refuses.
- *Anchor advances between the statement and the anchor read (a new revocation completed in between):* the anchor read returns the newer frontier ≠ snapshot frontier → rule 2 refuses; retryable. The safe direction costs availability only.
- *Anchor read returns a record from a different incarnation (including one disagreeing with the witness-bound lineage), a lower epoch than the bound head, or fails:* unverifiable → the attempt resolves unavailable (§2.6). Never a fallback to the presented store state.
- *Eligibility is issued or re-issued between the statement and the anchor read:* issuance does not move the frontier, so rule 2 is unaffected; the attempt decides on its snapshot's record under rules 3–4, which is exactly the snapshot semantics every other read in the system has. A *later* attempt reads the new record in its own statement, and rule 4 binds its presentation to that record — a post-rollback differing re-issuance refuses the original presentation there (§2.1.2).

*Why this closes RB-1:* a restore that removes any revocation changes the snapshot frontier, so no post-restore snapshot can equal the anchor; a fresh process reads the anchor from outside the restored unit and binds its lineage from the cross-witness in the store's own restore domain (§2.3.5), so restart does not help the adversary (RQ-2). Session revocations are inside the same frontier (RQ-5). During a genuine append→advance window an attempt resolves unavailable and is retryable, matching the codebase's existing `unknown` discipline; with no attack and the append protocol (§2.3.2) completing, frontier equals anchor and decisions proceed (RQ-6).

#### 2.3.2 The append→advance protocol: crash-safe record/provenance contract (findings B and D; blockers 1–2)

Anchor advancement and provenance are multi-write across two systems (the store, the anchor unit) with no distributed transaction. The protocol below is the complete contract S1/S3 implement; every crash point has a named state and a named resolution.

*Event identity.* Every revocation append handled by the composer is assigned a deterministic **eventId** before any write: `eventId = SHA-256(frame("atlas-anchor-event") || frame(scope) || frame(kind) || keyBytes || u64be(revokedAt))`, where `kind`/`keyBytes` are the §2.1.1 entry fields minus the tag. The same append input always yields the same eventId — retries and duplicates converge on one identity instead of creating parallel records.

*Fixed write ordering.* For each revocation append, the composer (which serializes anchor advances for a scope in the order store appends complete — the production composition has exactly one authorization-connection owner per scope) performs, in order:
1. **Intent.** Create-only provenance entry `{ eventId, kind, key, revokedAt, priorAnchor: { incarnation, epoch, count, frontierDigest }, status: "intent" }`. If an entry with this eventId already exists, the flow resumes from that entry's state (duplicate/retry) instead of writing a second intent. The recorded `priorAnchor` is **advisory only** (revision 3): it is what the anchor showed when the intent was opened, and it is never used as a CAS base — step 4 re-reads the anchor and proves against the fresh value. **Admission is serialized for the whole workflow (revision 4, INV-ADM).** Before creating an intent, the composer checks the provenance log for any non-terminal intent for the scope (states W1–W4, §2.3.3); if one exists, the new append is **not admitted** — no intent is created, no store append is attempted, and the caller holds a not-admitted outcome (an `unknown`-class outcome: nothing was written and nothing was promised) until the open workflow reaches a terminal entry, in this process or through §2.3.3 at restart. A restarted composer admits nothing until reconciliation has closed every pre-existing intent. It is therefore a protocol invariant, not a scheduling hope, that **at most one intent per scope is non-terminal at any instant**, and every store append happens inside that intent's workflow. Atlas's trace 3 (S = A ∪ {R1, R2} at the successor proof) is excluded by this invariant rather than answered at the proof step: serializing CAS calls alone never excluded it, because two appends could both commit before either CAS ran; serializing *admission* excludes it, because the second append cannot commit — cannot even be attempted — while the first intent is open.
2. **Store append.** The store's existing idempotent append. `appended` is the ordinary success shape. `already-present` splits by entry bytes (revision 3, blocker 2's timestamp rule applied in the normal path): if the stored entry for the key is byte-equal to this intent's entry, the append this intent names is already durable — proceed to step 3 (the entry may still be unanchored); if the stored entry's `revokedAt` differs, the row belongs to a *different event* — this intent is a **no-op duplicate**, it never advances the anchor, and it closes under §2.3.3's duplicate-satisfied rule once the owning entry is anchored. `unknown` stops the flow — see below.
3. **Frontier read.** The single-statement frontier (§2.3.1's frontier limb) → the candidate frontier F′, i.e. the full canonical set S′ the anchor would certify if this advance lands.
4. **Successor proof (revision 3, blocker 1 — mandatory on every advance, including duplicates).** Re-read the anchor record A_now. Advance is permitted only if **both** hold: (i) the anchored set of A_now — reconstructed from the provenance chain and verified against A_now's digest (§2.1), or, for the immediately preceding generation, the set this composer itself last acked — is a **subset** of S′; and (ii) S′ minus that anchored set is **exactly** this intent's single entry, byte-equal. The epoch is not consulted for membership: a higher epoch proves the record moved, never that the set grew monotonically — membership monotonicity is proven here, per advance, or not at all. If the proof fails (an anchored entry missing from S′ — the blocker-1 trace, where rollback removed R1 and S′ = {R2} fails (i) — or any extra/missing delta), **no CAS is attempted**: the flow reports `unknown`, surfaces `anchor-mismatch-unproven`, and the state is left to §2.3.3 reconciliation. Silently certifying S′ is the one outcome this step exists to prevent.
5. **CAS advance.** `advance(expected = A_now, next = { incarnation, epoch: A_now.epoch + 1, count/digest of F′, lastEventId: eventId, priorDigest, newDigest })`. The record as written embeds the prior and new frontier digests and the eventId, so every landed generation is self-proving. Because the composer serializes advances per scope and step 4 just re-read the anchor, a `false` here means the anchor moved outside this composer's serialization — itself an unproven state, handled below, never a cue to re-anchor.
6. **Ack.** On an acknowledgement-verified `true`, a create-only ack entry `{ eventId, generation, recordHash }`, where `generation` is the anchor object's new generation returned with the ack and `recordHash` is the hash of the record bytes as written — binding the event to the exact landed generation. **Then the witness observation** (§2.3.5): the composer appends the new head (incarnation, epoch, frontierDigest, recordHash, eventId) to the cross-witness log. The observation is part of the advance's completion, not an optional extra: an advance whose observation is missing is treated by §2.3.3 as landed-but-unwitnessed and is reconciled, never silently assumed.

*Outcome reporting.* The append's durable success is reported to its caller **only after step 6 completes in full — the ack entry and the witness observation both durable** (or after the convergence outcomes below, which likewise write both before reporting). Until then the outcome is `unknown` in the store's existing envelope sense. Per Atlas's finding B: a COMMIT-to-CAS gap with success withheld is not an acknowledged-revocation failure — no caller was ever told the revocation is durable — but the committed row is real, and §2.3.3/§2.3.4 define exactly what it means.

*Failure handling, per step:*
- **Step 2 resolves `unknown`** (store session loss / uncertain COMMIT): stop. The intent stays open. Nobody was told success. Resolution is by reconciliation (§2.3.3), which classifies the intent by entry bytes: stored entry byte-equal to the intent's → the append did commit, a candidate addition; stored entry for the key with different bytes → the row is another event's, and this intent is a duplicate candidate; key absent → the append did not commit, a void candidate.
- **Step 4 (successor proof) fails:** no CAS is attempted — this is a designed refusal, not an error. Report `unknown`, surface `anchor-mismatch-unproven`; decisions remain closed (the store frontier and the anchor already disagree, §2.3.1 rule 2). Reconciliation (§2.3.3) or the recovery ceremony owns the state from here; the append flow never retries its way around a failed proof.
- **Step 5 resolves `false` (definite conflict):** re-read the anchor. If the landed record's frontier equals F′ **and** its `lastEventId` equals this eventId, a duplicate advance (a retry whose ack was lost) already landed it: write the ack and the witness observation from the observed generation and report success. If the landed record is byte-identical to A_now (the failed CAS changed nothing — a generation race, not a value change), re-run the successor proof against it and retry the CAS once. **Any other landed value is never adopted**: do not treat the fresh winner as the new expected value, do not re-anchor to it; report `unknown`, surface `anchor-conflict-unproven`, and leave decisions failing closed until §2.3.3 reconciliation or the recovery ceremony resolves it.
- **Step 5 throws (uncertain):** re-read the anchor. Equal to the intended next record (frontier + lastEventId) → ack + witness observation + success. Equal to A_now → re-run the successor proof and retry the CAS. Anything else → the conflict path above. If the re-read itself fails → `unknown`; reconciliation resolves it later.
- **Crash between any two steps:** the durable state is exactly one of the state machine's states **W1–W4** (§2.3.3 — intent-without-append, append-without-advance, advance-without-ack, ack-without-witness-observation), each detectable from the provenance log, the anchor's retained generations, and point reads (and, for W4, from the witness log, §2.3.5), and each resolved by §2.3.3's phases — whose per-trace table covers every interruption point C0–C5. No state requires guessing.

*Audit completeness (defined, to be proven).* The audit rule over the provenance log + anchor generations: every anchor generation transition has exactly one acked intent whose embedded prior/new digests match the transition; every intent has exactly one terminal entry (ack, void, or duplicate-satisfied — §2.3.3); generations are contiguous per incarnation. The one-acked-intent-per-transition clause is **structural, not aspirational**: admission is serialized for the whole workflow (INV-ADM, step 1) — at most one intent per scope is ever non-terminal, the normal path runs that intent through one CAS, and reconciliation (§2.3.3) advances at most the single genuinely-new intent its classification can produce — so no generation transition can carry two intents, and no batch-ack semantics exist anywhere in the protocol. The S1 suite proves the rule against doubles under crash injection at each step boundary; the S8 harness re-checks it in the anchor-present topology. Until those suites run, completeness is a protocol goal, not a claim (§0 of revision 2, finding D).

#### 2.3.3 Restart reconciliation: an explicit state machine (finding B; blocker 2 — rebuilt in revision 4)

This section has failed three review rounds as prose — revision 2's subtraction, revision 3's classification rules — each time on a trace the text did not mechanically exclude. Revision 4 therefore specifies reconciliation as a **state machine**: the workflow's states are enumerated, every interruption point is named, reconciliation is four phases in a fixed order, and the per-trace table at the end runs every named trace to its classification. A classification below is never asserted; it is the output of a named phase applied to named durable facts.

**The workflow states.** One intent's passage through intent → store append → anchor CAS → ack → witness observation (§2.3.2) occupies exactly one state at a time, determined solely by durable facts:

| State | Durable facts | Meaning |
|---|---|---|
| **W0 — no intent** | No provenance entry for this eventId. | The append was never admitted (or is a fresh append not yet at step 1). Nothing is owed. |
| **W1 — intent open** | Intent entry durable; the intent's entry bytes are **not** in S (no store row carries them). | Admitted; the store append has not durably committed *this intent's* entry (it may not have run, may have resolved `unknown` without committing, or may have found a different event's row — told apart in Phase C). |
| **W2 — appended-unanchored** | The intent's entry bytes are in S; the entry is **not** in the anchored set A. | The revocation is committed in the store and not yet certified by the anchor. This is the **committed-unanchored** state (§2.3.4): decisions refuse (frontier ≠ anchor). |
| **W3 — anchored-unacked** | A landed anchor generation names this eventId as its `lastEventId`; **no ack entry** exists. | The advance landed; the provenance completion (ack) was lost. A provenance gap only — the anchor already reflects the revocation, so decisions are not blocked by this state. |
| **W4 — acked-unwitnessed** | The ack entry is durable; the witness log holds **no observation** for that generation. | The advance landed and was acked; the cross-witness observation was lost. A provenance gap only, as W3. |
| **W5 — complete** | Ack entry durable **and** witness observation durable for the landed generation. | The only state in which the append's success may be reported (§2.3.2), and the state every landed intent must reach. |

Two terminal side-states close intents that never advance: **T-DUP — duplicate-satisfied** (the intent's append resolved `already-present` against a *different* event's entry bytes; closed naming the owning eventId once the owning entry is anchored; never acked against a generation, never counted as an addition) and **T-VOID — void** (the intent's key is absent from S; its append never committed, and its caller holds `unknown`, so voiding betrays no one). Separately, **UNPROVEN** is a *scope* state, not an intent state: reconciliation cannot establish the facts above, so the anchor is frozen, decisions remain refused, and the recovery ceremony owns the scope. UNPROVEN is entered by named phase failures below — never by a classification merely being inconvenient.

**Interruption points.** A crash or uncertain outcome can interrupt the workflow at exactly these points; each leaves the intent in the state shown (a restart observes states, not intentions):

| Point | Interruption | State at restart |
|---|---|---|
| **C0** | After the intent write, before the store append resolves — including the append resolving `unknown` (uncertain COMMIT). | W1 if the append did not commit; W2 if it did (told apart by entry bytes, Phase C). |
| **C1** | After the store append commits, before the CAS — frontier read / successor proof in flight, or not yet begun. | W2. |
| **C2** | The CAS itself is uncertain (thrown) or returns a definite conflict — the outcome is decided by re-reading the anchor (§2.3.2 step 5), in-flow or at restart. | W3 if the intended generation landed; W2 if nothing landed; UNPROVEN (via Phase L/C) if a foreign value landed. |
| **C3** | After the CAS lands, before the ack entry is written. | W3. |
| **C4** | After the ack entry is written, before the witness observation is appended. | W4. |
| **C5** | After the witness observation. | W5 — no interruption is possible past completion. |

**The admission invariant (INV-ADM) — the multi-intent state cannot arise.** §2.3.2 step 1 serializes admission of the *whole workflow*: no intent may be created for a scope while any intent for that scope is non-terminal (W1–W4), and a restarted composer admits nothing until reconciliation has closed every pre-existing intent. The composer is the only creator of intents, and every store append runs inside the unique open intent's workflow. It follows mechanically — not by scheduling discipline — that **at most one intent per scope is ever non-terminal**, and that the candidate set S differs from the anchored set A by at most that one intent's entry. The singleton delta §2.3.2's successor proof demands is therefore guaranteed by construction; the proof still *verifies* it on every advance, and any deviation (an entry in S owned by no intent and not in A) is by definition out-of-protocol state, handled as UNPROVEN — never as a multi-entry advance. Serializing CAS calls alone could never give this: two appends could both commit before either CAS ran (Atlas's trace 3). Serializing admission gives it, because the second append cannot be attempted while the first intent is open.

**Reconciliation — four phases, in fixed order.** Before a restarted composer serves decisions for a scope, and whenever a decision attempt observes frontier ≠ anchor outside an in-flight append, reconciliation runs. The order is the repair for Atlas's trace 1: landed transitions are established **before** ack completeness is examined, and the observation pass runs over **transitions**, not over open intents (trace 2).

- **Phase L — establish what landed (first, always).** Read the anchor record, the witness head (§2.3.5), and the provenance log. *Witness gate:* if the anchor's incarnation disagrees with the witness-bound lineage, or the anchor's epoch is behind the witness head for that lineage, this is not reconciliation's to repair — the scope is **unverifiable** (§2.6) and the recovery ceremony owns it; reconciliation writes nothing. *Replay:* replay the retained anchor generations in order from genesis (S1 requires them readable, §4). Each generation's record names its `lastEventId` and embeds its prior/new frontier digests; the replay resolves each `lastEventId` to its provenance intent, accumulates that intent's entry bytes, and requires digest(accumulated) to equal the generation's embedded new digest and the accumulated-before digest to equal its embedded prior digest. A `lastEventId` that resolves to no intent, or any digest step that disagrees, **fails Phase L → UNPROVEN**, and reconciliation writes nothing. The replay must terminate at the current anchor record — accumulated set, count, and frontierDigest equal to the record's, epoch equal to the generation count — or Phase L fails the same way. The accumulated set is the anchored set **A**, established from the anchor's own generations. *Ack cross-check (audit only, never a gate):* every ack entry must be consumed by the replay — its eventId among the replayed transitions, its (generation, recordHash) matching that generation. An ack the replay does not consume is a claim about a transition that did not land → **UNPROVEN**. The converse is *not* a failure: a replayed transition with no ack is W3, already-landed, and proceeds to Phase O. (Revision 3 compared the anchor against a reconstruction from acked intents and stopped on mismatch *before* replay; that ordering is what made {R1}-landed-unacked unreachable. The acked-intent reconstruction survives only as this cross-check.)
- **Phase O — missing-observation pass (over landed transitions).** For every transition the replay consumed, in generation order: if no ack entry exists for its eventId, write it now — `{ eventId, generation, recordHash }` taken from the replayed generation (facts about the past, from the anchor's own retained record). If the witness log holds no observation for that generation (matched on incarnation, epoch, eventId), append it — `{ scope, incarnation, epoch, frontierDigest, recordHash, eventId }` from the same generation. Phase O moves no anchor and certifies nothing new; it completes the provenance of transitions already landed. It is what closes W3 (ack missing) and W4 (observation missing — including transitions whose intents are *terminal* in the provenance log, which revision 3's open-intent classification never revisited: Atlas's trace 2). Phase O's writes may stand even if a later phase lands the scope in UNPROVEN: they are completions of landed history, not movements of the anchor.
- **Phase C — classify the open intent; account for S.** Read S (S2's full canonical set read — reconciliation only, never decisions). By INV-ADM there is **at most one** open intent (an intent with no terminal entry and not completed by Phase O); if more than one is found, the invariant was violated outside the protocol and the scope is **UNPROVEN**. Classify the open intent by its entry bytes against A and S:
  - **Already-landed** — the replay consumed this eventId. (After Phase O the intent is in fact complete; the classification records that it was landed, not open business.) No anchor movement.
  - **Genuinely new** — the intent's entry is in S (byte-equal), not in A, and the replay did not consume it: the append committed and no transition certifies it yet (W2). → Phase A.
  - **No-op duplicate** — the intent's key is present in S or A but the stored/anchored entry bytes **differ** from the intent's entry (a different `revokedAt`): the row belongs to the owning event, whose entry it is. → once the owning entry is in A (it is, after Phase L, or the owning transition was completed in Phase O), write the **duplicate-satisfied** terminal entry naming the owning eventId (derived deterministically from the stored entry bytes). If the owning entry is *not* in A and is owned by no landed transition — an unexplained row — the scope is **UNPROVEN**: a duplicate cannot be satisfied by an unowned entry.
  - **Void** — the intent's key is absent from S (W1 with no commit). → write the void entry (T-VOID).
  *Accounting:* every entry in S must be in A, or be the open intent's entry (genuinely-new or the duplicate's owning entry), and every entry of A must be present in S. An entry of A missing from S is an anchored revocation removed (rollback); an entry of S with no owner is out-of-protocol state. Either → **UNPROVEN**: the anchor does not move, no intent is advanced, decisions remain refused, the mismatch is surfaced as `anchor-mismatch-unproven`, and resolution is the recovery ceremony — never an automatic re-baseline.
- **Phase A — advance the genuinely-new intent (at most one, singleton-proven).** If Phase C produced a genuinely-new intent, run §2.3.2 from step 3 for it: frontier read (F′ = S), successor proof against the current anchor — under INV-ADM and Phase C's accounting, S ∖ A is *exactly* this intent's single entry, which the proof verifies rather than assumes — then CAS, ack, witness observation. The intent ends in W5. Any CAS outcome other than the expected landed value stops here: the flow re-enters this section on the next reconciliation run, where Phases L–C reclassify from durable facts. No other advance is possible in a reconciliation run, because no other unanchored entry can exist.
- **Completion.** Reconciliation succeeds only when: Phase L terminated at the current record; Phase O is drained (every landed transition acked and witnessed); Phase C classified the open intent, if any, to a terminal class; Phase A advanced the genuinely-new intent, if any; and the final reads agree — S = A and the witness head equals the anchor head. Only then does the scope serve decisions. Every other exit is UNPROVEN or unverifiable, with the anchor unmoved.

#### 2.3.4 Committed-unanchored: the named state

A revocation that has committed in the store but is not yet reflected in the anchor leaves the scope in the named state **committed-unanchored**. In that state: the revocation row is real and visible to reads; decisions refuse (frontier ≠ anchor, §2.3.1 rule 2) — the failure direction is closed; the append's caller holds `unknown`, not success; and the state exits only through §2.3.2 completion or §2.3.3 reconciliation, where the intent is classified already-landed, genuinely new (and advanced in Phase A), no-op duplicate, or void — the state has no other exits. In §2.3.3's state machine this state is **W2**; the later incomplete states (W3 anchored-unacked, W4 acked-unwitnessed) are provenance gaps only — the anchor already reflects the revocation, so decisions are not blocked by them — and they close through the missing-observation pass (Phase O), never by anchor movement. It is never resolved by waiting, by re-reading until values happen to match, or by moving the anchor to an unproven value.

#### 2.3.5 The cross-witness: an independent lineage high-watermark (blocker 3)

Revision 2's incarnation detection was self-referential (blocker 3): a fresh process learned the expected incarnation from the anchor unit's own provenance chain, so an anchor-unit restore that presented an older, internally consistent chain was undetectable in principle. The mechanism added here is the independent lineage the review requires — independent in the only sense that matters for this adversary: it lives in a **different restorable unit** from the anchor.

- **What it is.** An append-only **anchor-observation log** in the authorization database's restore domain: one row per observation `{ scope, incarnation, epoch, frontierDigest, recordHash, eventId, observedAt }`, written (a) at genesis (epoch 0, the genesis event) and (b) after every acked authorization-anchor advance, as the final step of §2.3.2. The log's head for a scope is the lineage high-watermark: the greatest (incarnation, epoch) the store domain has ever witnessed, with the digest and record hash it witnessed.
- **Why it cannot ride the existing connection.** The shipped authorization connection's preflight admits **exactly three relations** in the authorization schema — its schema check fails on a fourth (verified, §7) — and the store module's relation contract is frozen at those three. The witness is therefore its **own module, own dedicated session, and own preflight profile**, over a witness schema in the same database (same PITR domain — that shared fate with the store is the point: the witness must survive exactly the events the anchor does not, and vice versa), with INSERT/SELECT-only grants and the same UPDATE/DELETE/TRUNCATE prohibitions the authorization preflight enforces. This is new surface for S3 (§4), not a change to the shipped store or connection.
- **Who writes, who reads.** The composer is the only writer (one per scope, the same serialization owner as the advances). Readers: the composer at scope open (binding the expected lineage before any decision is served), §2.3.3 reconciliation, and qualification/audit tooling. The anchor provisioning/admin principal holds no witness capability; no store role holds anchor credentials (§2.8) and the witness writer holds no anchor-unit write capability beyond the composer's own — the witness is written *by* the advance flow, never *to* the anchor.
- **Detection rules.** At scope open and at every reconciliation: witness incarnation ≠ anchor incarnation → the anchor lineage is foreign (delete/recreate or wrong unit) — unverifiable, qualification-invalidating for the scope until the ceremony. Witness (epoch, digest, recordHash) **ahead of** the anchor for the bound incarnation → the anchor has regressed (restore/rollback of the anchor unit) — unverifiable, same handling. Anchor ahead of the witness **only** by landed transitions whose witness observations are missing → the crash gap between ack and observation (states W4, and W3 where the ack is also missing); §2.3.3's missing-observation pass (Phase O) writes the missing acks/observations over the landed transitions and proceeds — over *transitions*, not only over open intents: an acked intent is terminal in the provenance log, but its transition is still owed its observation (Atlas's revision-3-review trace 2). Anchor ahead of the witness in any other shape → unproven. A witness that is *behind* because the database domain itself was rolled back is consistent with the rolled-back frontier and is caught by §2.3.1's frontier equality instead — each unit's rollback is witnessed by the other, which is the whole construction.
- **What it does not do.** It is detection, not prevention: it does not stop a provisioning principal from restoring the anchor unit; it makes the restore visible and disqualifying (§2.6). It does not survive a **joint** rollback of the database domain and the anchor unit to a consistent older pair — that remains outside INT-4's adversary model and is recorded in §5, now stated for the witness explicitly rather than by implication. And it does not prove custody: Q-C remains UNPROVEN (§3), with the witness's own grant/preflight audit added to its proof obligations.

### 2.4 History anchor — durable floor (RB-2 / RQ-2)

The terminal-certificate module's floor logic is sound; only its storage is wrong (process memory). Verified shape at `aacd44c2` (§7): `qualifySnapshot` rejects a snapshot below the floor's revision, recomputes the digest of the snapshot's prefix at the floor revision and rejects on divergence, and then *sets the floor to the snapshot it just qualified* — floor movement is already tied to a continuity proof against the previous floor. The design makes the floor durable without changing `qualifySnapshot`'s rules, and — per finding E — priming is subordinated to that same discipline:

- *Priming as candidate, never as replacement.* A new exported function (e.g. `primeFloor(domain, checkpoint)`) offers the durable history anchor to the module when an adapter/domain is opened:
  - If the domain has **no** in-process floor (fresh process), the durable anchor installs as the floor. It is not a new trust decision: it is the previous trusted floor in durable form, and the first snapshot still has to satisfy the existing revision + prefix-at-floor checks against it — a rolled-back snapshot arrives below it or with a divergent prefix and throws `terminal rollback` in a fresh process, which is precisely RQ-2.
  - If the domain **already has** a floor, priming does **not** replace it. The offered value is held as a *candidate floor*. The retained floor stays authoritative. The candidate is adopted only through a qualifying snapshot: the snapshot must first qualify against the retained floor under the existing rules; then, if the snapshot's revision is at least the candidate's, the module checks the snapshot's own prefix at the candidate revision against the candidate digest — equality means the candidate lies on the same proven lineage, and the floor then advances exactly as `qualifySnapshot` already advances it (to the qualifying snapshot). Divergence means the durable anchor and this process's lineage fork: the candidate is rejected, the retained floor is unchanged, the fork evidence is preserved, and the event is surfaced. Priming first and checking later — v1's wording — would have discarded exactly that evidence, and is withdrawn. Both checks in this adoption path are **staged** (§2.4.3): they run without moving the floor, and publication is the final step, after candidate continuity *and* any pending-event proof (§2.4.2) have passed — a candidate that fails any check leaves the floor byte-identical (INV-F8).
- *Advance — under a recorded pending event (revision 3, §2.4.2).* The PostgreSQL adapter's `compareAndAppend` already performs a byte-conditional UPDATE (a storage-level CAS) and only then advances the in-process floor via the post-commit `qualifySnapshot`. The design adds the anchor advance **around** that call, not inside it: before the call, the composition records a history pending event (prior checkpoint pair + the full certificate); after the COMMIT, it CAS-advances the durable history anchor from the prior pair to the **derived** successor pair and acks the event. Anchor-advance failure after a committed append resolves the append's outcome as unknown (the adapter already has this exact outcome shape for lost-holder cases) and the open event is reconciled under §2.4.2 — by *derivation and prefix proof*, never by adopting an observed checkpoint: a valid above-anchor state in the store is not, by itself, proof that the intended write landed (blocker 4). A durable floor lagging behind the store is safe — floors only reject regression, they never reject advance — and a rolled-back snapshot arrives **below** the durable floor and throws.
- *Scope honesty:* this covers the PostgreSQL native-history surface — the surface the production composition uses. Any other history surface (file/object adapters) is outside this design's claim until it grows the same priming/advance wiring; §5 carries this.

#### 2.4.1 Floor/restore invariants (decision 3 — S5)

- **INV-F1.** Priming never lowers, replaces, or clears an existing in-process floor.
- **INV-F2.** A candidate floor is adopted only via a snapshot that (a) validates against the retained floor and (b) proves prefix continuity through the candidate; adoption is the qualifying snapshot's own floor advance, not the priming call. Both validations are **staged** (§2.4.3): neither moves the floor while it runs, and publication happens only after both — and any pending-event proof (§2.4.2) — have passed.
- **INV-F3.** In a fresh process the durable anchor is the floor of record; the first qualification is checked against it with the module's existing revision/prefix rules, unmodified.
- **INV-F4.** No read path adopts an external checkpoint (anchor, supplied, or observed) as a floor without a qualifying snapshot. Ordinary reads bless above-floor state only through the prefix proof inside `qualifySnapshot` — there is no silent blessing. Because the shipped adapter's read path invokes `qualifySnapshot` with the real domain key (it publishes floor movement on every read, §7), a **recovery or candidate read** — any read whose purpose is to evaluate a state the process has not already qualified — must use the staged evaluation path (§2.4.3), never the ordinary read.
- **INV-F5 (writer/reader model).** One composed writer per domain in the production composition. The terminal-certificate header itself records the boundary: permanent process registry keys bind (householdId, ledgerNamespace) to declared serialization/history authorities, and "independent registries/old binaries and rollback of the checkpoint authority itself remain unqualified production prerequisites." Concurrent writers or independent registries are therefore outside the qualified model, not silently accommodated. A stale reader's floor moves only through its own qualifications (INV-F4).
- **INV-F6.** Durable-anchor advancement after `compareAndAppend` follows the pending-event discipline of §2.4.2 (recorded intent, derived successor, prefix proof); a lagging durable floor is a safe, named state, never repaired by adopting an observed value unproven.
- **INV-F7 (pending events).** No history anchor advance occurs without a recorded pending event whose derived successor pair (§2.4.2) is the advance's target. An observed checkpoint — however valid, however far above the anchor — is never an advance target by itself.
- **INV-F8 (floor unchanged on candidate failure).** A candidate (floor candidate, recovery state, restore state) that fails any staged check leaves the in-process floor byte-identical to its pre-evaluation value. Floor movement is publication, and publication is always the last step of a fully passed evaluation.

#### 2.4.2 History pending events and successor proof (blocker 4)

The authorization side proves an intended successor from recorded intents and a set digest; the history side needs its own form of the same proof, because its state is a byte chain, not a set. Revision 2's reconciliation-by-observation is withdrawn: that a store snapshot is a *valid* above-anchor prefix/successor says nothing about whether it is the successor **this** unacknowledged write intended — a later legitimate append, or any other append that passed the byte-CAS, produces equally valid above-anchor state.

*The pending event.* Before the composition invokes `compareAndAppend` for a domain, it records a create-only pending event in the anchor unit's provenance log: `{ eventId, domain, priorPair: { revision, digest }, certificate, status: "intent" }`, where `eventId = SHA-256(frame("atlas-history-event") || frame(householdId) || frame(ledgerNamespace) || u64be(priorPair.revision) || frame(priorPair.digest) || frame(C.digest(certificate-payload)))` — deterministic in the same sense as §2.3.2: retries of the same intended append converge on one event. The certificate is recorded in full: it is the unit of proof below.

*The successor is derived, not observed.* The intended successor pair P′ is a pure function of the pending event and the history the append extends: the adapter itself constructs it pre-COMMIT as `(priorRevision + 1, C.digest({schema, householdId, ledgerNamespace, revision: priorRevision + 1, records: [...priorRecords, certificate]}))` (§7 — the shipped code computes exactly this payload and digest before its byte-conditional UPDATE). The composition derives the same P′ from the prior snapshot it read and the recorded certificate; the derivation uses the module's own digest discipline, so P′ is checkable by anyone holding the prior state and the certificate, and is never taken from the store's say-so.

*Normal completion.* `compareAndAppend` resolves `true` (COMMIT affirmed) → CAS-advance the history anchor `expected = priorPair → next = { incarnation, …P′, lastEventId: eventId }`; on the ack-verified `true`, write the ack entry. `false` (definite CAS miss — the byte-CAS matched nothing) → the append did not land; void the event. A throw / lost holder / post-commit qualification failure resolves the append `unknown` (the shipped outcome shapes) and leaves the event open for reconciliation.

*Reconciliation of an open history event* (at adapter open, and whenever the durable anchor disagrees with a staged read of the store):
1. **Stage** the store's current snapshot without publishing floor movement (§2.4.3) and validate it against the retained floor / durable anchor under the module's existing rules.
2. Classify the event against the staged state S and the anchor A:
   - **Already-landed** — A's pair equals P′ and A's `lastEventId` equals this eventId (the advance landed; the ack was lost). Write the missing ack. No movement.
   - **Genuinely new** — A equals `priorPair` and S's checkpoint equals P′: the intended append is the current head and nothing has certified it yet. CAS-advance A → P′ (expected = `priorPair`), ack.
   - **Landed-and-superseded** — A equals `priorPair`, S is *beyond* P′, and S proves prefix continuity through P′: the digest of S's own prefix at P′.revision equals P′.digest **and** the record at position `priorPair.revision` in S is byte-equal to the recorded certificate. The intended append demonstrably landed (its exact bytes sit at the exact position in a proven lineage) and later appends — each with its own pending event — built on it. Advance A → P′ (one CAS), ack, then reconcile the subsequent events in order, one CAS per event, exactly as §2.3.3's Phase A advances proven successors.
   - **Void** — S's checkpoint equals `priorPair` (byte-equal): the append never landed. Void the event.
   - **Unproven** — anything else: S diverges at or before `priorPair` (prefix digest mismatch), S's record at the certificate's position differs from the recorded certificate, S is beyond P′ without prefix continuity through it, or A names a pair that is neither `priorPair` nor P′. The anchor does not move; the fork/mismatch evidence is preserved and surfaced; resolution is the recovery ceremony. A *valid* S, standing alone, changes nothing in this classification — validity is a precondition for staging, never the proof.
3. If there are no open events and the anchor disagrees with the staged state, that is unproven by definition (the §2.3.3 rule, restated for this surface).

#### 2.4.3 Staging: validate first, publish floor movement last (blocker 4)

The shipped `qualifySnapshot` fuses validation and publication: it runs its full check suite (identity, digest recomputation, per-record validation, floor revision/prefix checks) and, as its **final** step, sets the floor to the snapshot it qualified (§7). Within its own contract that is safe — a candidate that fails any check throws *before* the floor moves. The hazard Atlas names is real one level up: in the candidate-floor adoption (§2.4) and in §2.4.2 reconciliation, floor movement must wait on checks that live **outside** `qualifySnapshot` (continuity through a candidate floor; pending-event derivation), and the adapter's ordinary read path invokes `qualifySnapshot` with the real domain key — so merely *reading* a candidate state through the adapter publishes it as the floor before those external checks have run.

The design therefore requires a **check/publish split** in S5, generalizing a pattern the shipped adapter already uses: its `compareAndAppend` validates the candidate snapshot under a **throwaway domain key** (`{...terminalDomain}` — a fresh WeakMap key with no floor) precisely so that "a definite CAS miss must not create a fictitious higher floor" (§7). S5 exports that staging as a first-class seam:
- `checkSnapshot(domain, snapshot)` — the full `qualifySnapshot` validation against the domain's *current* floor, executed so that no floor state changes (throwaway key, or an equivalent non-mutating path); returns the validated snapshot or throws, exactly as today.
- `publishQualification(domain, snapshot)` — sets the floor to a snapshot that has passed `checkSnapshot` **and** every external validation its context requires; this is the only floor-moving call a candidate path may make, and it is always the last step.
- The writer path (`compareAndAppend`'s post-COMMIT qualification of its own committed append) is unchanged: its candidate was validated pre-COMMIT by the shipped staging trick, and its publication certifies the writer's own committed work, not an external candidate.
- Priming, candidate-floor adoption, reconciliation reads, and restore verification (§2.5) use staged evaluation exclusively (INV-F4, INV-F8).

### 2.5 Restore path — anchors become verified, not trusted (RB-3 / RQ-4)

`installRestoreCandidate` / `verifyRestoreInstall` keep their existing shapes (injected one-shot maintenance session, incumbent quarantine in one transaction, `installed-unverified` semantics, `'verified' is not reopen authority`) and gain an anchor-verification step that demotes the operator-supplied anchors from *trusted input* to *candidate claims*:

1. **Pre-install:** the supplied `anchors.history` must equal the durable history anchor (revision + digest) and the supplied `anchors.ledger` must equal the financial pin as read from the named pin store. A genuine-but-stale anchor set now mismatches the durable records and the install is **refused** with a new reason (`anchor-stale`), before any quarantine or write. The provenance fields the install report records (source, read time, hash — C-5) are the anchor-unit reads, not the operator's assertions.
2. **Post-install verify:** the existing readback checks stand, and verify additionally re-reads the durable anchors and confirms the installed checkpoint/head still equal them.
3. **The install never advances an anchor.** Anchor records move only through the live write paths (§2.3, §2.4) and the genesis procedure (§2.6). A legitimate restore of the true latest state passes by equality; any restore to an older state fails by inequality. There is no "restore mode" that suspends the check — suspending it would reopen RB-3 by definition.

#### 2.5.1 Restore invariants (decision 3 — S7)

- **INV-R1.** Supplied anchors are claims. Install proceeds only on equality with the durable anchors read in the same maintenance session, before any write.
- **INV-R2.** Install and verify never advance, create, repair, or re-baseline any anchor record.
- **INV-R3.** On any mismatch the incumbent bytes are untouched: refusal happens before the install transaction opens — no quarantine, no partial write.
- **INV-R4.** Post-install verify re-reads both the durable anchors and the installed bytes; equality with both is required, and `verified` still is not reopen authority (shipped semantics unchanged).
- **INV-R5 (baseline rule).** The durable anchor values used for comparison are captured and frozen before the install attempt. A refused install never updates the comparison baseline from post-attempt observations (the baseline-sequencing requirement of #755 comment 6449825208, §2.6.1).

### 2.6 Genesis, incarnation, absence, and failure behaviour

- **Genesis** mirrors the financial store's own pattern (`pinStore.advance(null, {revision: 0, …})`): a named, separately authorized provisioning procedure creates the three anchor records against absent state, and with them the scope's **incarnation** (§2.1.1) and the provenance chain's genesis entry. Absence is proven absence only (a malformed or unreadable anchor read throws, per the pin contract — never treated as zero).
- **Absent anchor on a live domain is unverifiable, therefore refusal** — at decision time, at snapshot qualification, and at restore. The only path from absence is the genesis procedure; there is no silent re-baseline anywhere in this design (checklist R-5).
- **Anchor-unit restore is a qualification-invalidating event, and it is detectable — on the narrowed basis of blocker 3, stated exactly.** Revision 2 claimed incarnation detection "on its face"; that phrasing is withdrawn — a record's incarnation detects nothing without an independent expectation to compare it against. The detection bases are: (i) for the authorization anchor, the **cross-witness** (§2.3.5): a delete/recreate presents a foreign incarnation against the witness head, and a restore presents an epoch/digest behind it — both refuse at scope open and at reconciliation, and neither depends on any process having observed an intermediate absence; (ii) for the history anchor and the financial pin, the **data unit's own head** at every use: a restored anchor pair that the terminal-history relation / financial store contradicts (behind its proven head in a way priming cannot heal, ahead of it, or digest-divergent) fails §2.4/§2.5 verification — the pair is a claim about data held elsewhere, and the elsewhere witnesses the *data*. **Narrowed in revision 4:** this detects stale or divergent pairs; it does **not** prove the anchor record's incarnation — the pair does not carry one (§2.1.1) — and a recreated unit faithfully copying the current pair passes it. Incarnation continuity for these two records is UNPROVEN and rests on §2.8 and the ceremony; (iii) provenance-chain verification (genesis head + per-generation ack chain, §2.3.2) — necessary internal consistency, **not** independent detection: a restored older chain passes it, which is exactly why (i)/(ii) exist; (iv) the owner-held notarization, if adopted, pins the expected head digests + incarnation at ceremonies — a complement and a ceremony input, never the mechanism. If the owner ever restores the anchor unit itself, recovery is a re-qualification ceremony (re-derive the expected records from the stores' provenance, the witness, and the notarization if adopted), never an automatic resumption. This is stated as a procedural requirement for the runbooks, not a mechanism.
- **Fail-closed everywhere (RQ-3, as mapped in §2.6.1):** unverifiable anchor = refusal, at every consumer. No consumer in this design falls back to the presented state, and the mechanism performs no repair writes on any refusal path.

#### 2.6.1 RQ-3 case map: protected units, attack destinations, baselines (finding F; blocker 5)

"No repair writes" is the mechanism's *behaviour on refusal*; it is not, by itself, preservation. Revision 3 adds the column revision 2's map lacked: an explicit **RQ-3 status** per case (blocker 5). RQ-3 as written requires **exact-latest durable-byte preservation**. Where an attack has already replaced bytes at a destination, this mechanism preserves the *baseline*, detects the replacement, and refuses to use the attacked state — it does not preserve the genuine latest bytes at that destination, and the affected cases are marked **UNMET** rather than argued around. The requirement is not weakened here; changing it is the decision desk's act, requested as a recorded disposition in §6.

Three consequences are stated without weakening RQ-3. First: where an attack has *already* replaced a store's bytes, the genuine latest bytes may be destroyed at that destination; the mechanism cannot un-destroy them, and does not pretend to. What it guarantees is that the destroyed state is never *used*, never *repaired into a new baseline*, and never *mistaken for latest* — the pre-attack baseline (anchor + frozen qualification baseline) survives outside the destination, and restoration compares against it. Second: the **baseline-sequencing rule** from Atlas's INT-5 readiness review (#755 comment 6449825208) is a design requirement on every qualification or recovery procedure built on this mechanism: pre-mutation counts/setup baselines are retained separately; the qualification baseline is captured and frozen after setup/control and immediately before each planned attack (or install attempt); refusals are compared against **that** frozen baseline; the baseline is never replaced with post-attack state. Mismatches are resolved explicitly through that procedure — surfaced, named, and dispositioned — never silently absorbed. Third (revision 3): the UNMET markings above are the design's final position on RQ-3, not a problem it routes around. INT-5 may not claim RQ-3 for the marked cases on the strength of this design. Either the decision desk records a requirements disposition amending what RQ-3 demands (for example, to detection + refusal + recoverability from separately held backups), or the marked cases remain UNMET and gate accordingly (§6, Atlas item 5).

### 2.7 What this design deliberately does not use: fencing

Fencing is **UNSOLVED** (Rev 3 CAS fencing was rejected) and this design neither implements nor assumes it. The anchor CAS gives *detection* (stale state cannot pass verification) and *monotone advance* (records cannot move backward through their write path). It does **not** fence a stale or partitioned writer out of the stores themselves: such a writer can still append to a store, but its appends cannot pass decision/restore verification without the anchor, and anchor advance from a stale expected value fails as a definite conflict. If any future requirement demands exclusion of the writer rather than refusal of its effects, that is a fencing property — marked **OPEN**, owned by the P-8 disposition in the INT-5 spec, not by this design. Atlas's review (decision 4) supplies **no** accepted-open-risk disposition and no owner activation-risk acceptance, and this revision neither requests one implicitly nor treats design adoption as implying one: P-8 stands exactly as it stood.

### 2.8 Principals and the anchor unit's protection model (finding C)

Generation CAS alone stops stale-token writers. The rest of finding C is a principal problem, answered here as **provisioning requirements** (the choices and any spend are Dale's, §6; satisfaction is Q-C's proof obligation, §3):

- **Anchor-writer principal** (held by the running composition, one per deployment): may read the anchor records, create provenance objects (create-only), and conditionally write record objects under a generation precondition. It may **not** delete any object, write any object unconditionally, alter versioning/lifecycle/policy, or create a genesis (records against absent state are refused to it after genesis — genesis-shaped creates are the provisioning principal's alone). Under this principal, the anchor's history can only move forward through the §2.3.2/§2.4 protocols.
- **Anchor-reader principals** (decision path, adapter priming, restore verify, qualification tooling): read-only on records and provenance. No write of any kind.
- **Witness principals (revision 3, §2.3.5).** The cross-witness log lives in the authorization database domain, outside this unit's principal model entirely: its writer is the composer, through the witness module's own dedicated session under INSERT-only discipline; its readers are the composer and qualification tooling. The anchor provisioning/admin principal holds **no** witness capability — restoring or recreating the anchor unit cannot rewrite the high-watermark that detects it — and no witness principal holds any anchor-unit capability. This asymmetry is the detection mechanism of §2.6(i); collapsing it (one principal holding both) collapses the claim, and is recorded as a provisioning prohibition, not a preference.
- **Provisioning/admin principal** (owner-held, never held by the running server): creates the bucket/project, sets versioning + retention, performs genesis, and is the only principal that *can* delete or restore the anchor unit. Its every use on the anchor unit is a qualification-invalidating event by procedure (§2.6) — the model does not try to make owner-level restore safe; it makes it visible (incarnation/epoch/chain discontinuity) and disqualifying.
- **Separation:** no store role holds anchor credentials of any class, and no anchor principal holds store credentials. The RB-1/RB-3 adversary — who holds store restore capability — holds, by construction of the grant model, no anchor capability at all; reaching the anchor requires the provisioning principal, a different custody class.
- **Honest limit:** a principal who holds *both* the provisioning/admin channel *and* the owner notarization channel can defeat detection as well as prevention. That actor is the owner themselves or a total custody compromise; it is outside INT-4's adversary model and is recorded in §5, not designed against.

## 3. Explicit answers to the INT-5 RQ-7 questions (Q-A..Q-E)

**Q-A — Location.** The anchor/epoch lives in a dedicated object-storage bucket/prefix (Candidate B, the design's candidate; Candidate A — a distinct Neon project — is the retained alternative; **neither adopted**, decision 1), holding the financial pin, the authorization anchor, and the history anchor, plus an append-only provenance log. Its restore boundary is independent by construction: it is not part of either store's database, schema, snapshot, or maintenance-restore path, and no operation in the RB-1/RB-3 adversary model touches it. The evidence of independence must be demonstrable, not asserted: the INT-5 step-14 custody proof attempts the rollback against the anchor with the real provider mechanism and records the attempt (see Q-C — unproven until then).

**Q-B — Writers and readers.** Writers: exactly the live write paths, one per record — the financial store's existing genesis/promotion flows (pin); the authorization composition layer, on every committed revocation append, operation or session, under the §2.3.2 protocol (authorization anchor); the composition around the PostgreSQL adapter, on every committed `compareAndAppend`, under the §2.4.2 pending-event protocol (history anchor). Anchor advance is part of each flow's durable-success contract. The restore path writes **no** anchor, ever (INV-R2). The **cross-witness** (§2.3.5) has exactly one writer — the composer, appending the observation as the final step of each authorization-anchor advance (and at genesis) — and its readers are the composer at scope open, §2.3.3 reconciliation, and audit tooling. Readers of the anchors: the final-decision integration (authorization anchor, after its combined statement, §2.3.1); the terminal-certificate priming path (history anchor, at adapter open, as a candidate floor under §2.4); the restore install/verify path (history anchor + pin, pre-install and at verify); reconciliation (§2.3.3, §2.4.2); and qualification/audit tooling (provenance log). All writes are CAS advances under the principal model of §2.8 (credential custody itself is Dale's, §6).

**Q-C — Adversary independence. UNPROVEN.** The argument, as far as it goes: the RB-1 adversary restores a PostgreSQL checkpoint — the anchor is not in that database, project, or provider system, so the restore cannot carry it. The RB-3 adversary supplies anchors to the maintenance restore — under this design supplied anchors are claims verified against the durable records (INV-R1), so supplying stale ones produces a refusal, not an install. Replacing the anchor directly requires defeating the principal model (§2.8): the writer principal cannot delete, overwrite unconditionally, or re-genesis; backward movement is not expressible as an advance (no rollback, no fork, no skip); a delete/recreate or restore by the provisioning principal is **detected** on the bases §2.6 names — for the authorization lineage, the cross-witness high-watermark (§2.3.5), which the anchor-side principals cannot rewrite; for the pin and history records, the data units' own heads at every use — a staleness/divergence check only, which does not establish those records' incarnation (revision 4, §2.1.1: the pair carries no incarnation and cannot prove one; their incarnation continuity is UNPROVEN with the rest of this answer). Revision 2's stronger phrasing — detection from the unit's own chain — is withdrawn (blocker 3): the provenance chain proves internal consistency only, and detection is claimed solely against restores confined to one unit, never against a joint rollback (§5). **What remains unproven, as explicit proof obligations:** (i) that the provisioned principal restrictions in fact deny the store-restore operator every anchor capability (a grant-model audit, not a document claim); (ii) that the chosen provider's generation/CAS and create-only semantics behave as the transport contract requires under the real mechanism; (iii) the INT-5 step-14 demonstration — attempt the anchor rollback with the real provider mechanism under the frozen plan and record the custody-attempt evidence; (iv) (revision 3) that the cross-witness's own grants, preflight, and append-only discipline hold as provisioned, and that its head is in fact readable at every scope open the design requires. Until (i)–(iv) land, Q-C is a candidate boundary with a defined proof, not RQ-7 satisfaction. Offline, slice S8 (§4) gives the harness an anchor-present topology so the same attempts are executable against doubles (pattern proof only).

**Q-D — Checklist custody rows. UNPROVEN in part.** **C-5:** the authoritative source for anchors and pin is named — the anchor unit — and the §2.3.2 protocol produces a provenance record (source event, read/observed time, prior/new hashes, generation) at the moment of each advance, in a fixed write order with idempotent event identity. Audit completeness across crashes is *defined* (§2.3.2) and must be *proven* by the S1 suite and re-checked by S8; this document does not claim every advance already has complete C-5 provenance. **C-6:** the real pin store is named — the implementation of the store's injected `pinStore.read/advance` surface over the anchor unit, using the object adapter's documented transport contract (generation-bound conditional writes; CAS never emulated). The pin advance log records each transition's expected pair, next pair, and acknowledgement-verified result (`true` / definite-conflict `false` / thrown-uncertain), matching the transition discipline `pinStore.advance` already specifies. **BR-29 equivalence is NOT claimed**: the frozen BR spec's BR-29 text lives in the offline frozen package and has not been re-read (§7); C-6's own wording is the requirement used, and equivalence awaits that reading.

**Q-E — Failure behaviour, with RQ-3 marked honestly (blocker 5).** Fail-closed behaviour is confirmed, not weakened: at every consumer, an unavailable or unverifiable anchor is a refusal — decision resolves unavailable, snapshot qualification throws, install/verify refuses — and never a fallback to the presented state, per checklist R-5. No repair writes occur on any refusal path. **But refusal is not preservation, and revision 3 stops letting the two share a sentence.** RQ-3 requires exact-latest durable-byte preservation; per the §2.6.1 map, that requirement is **UNMET** for the authorization-store case, the `terminal_history` case, the anchor-unit case, and the financial store under direct byte replacement — in each, once an attack has replaced bytes at the destination, this mechanism preserves the *baseline* (never re-baselining from post-attack state), refuses to use the attacked state, and leaves recovery of the genuine bytes to separately held backups and the frozen-baseline procedure. The single non-UNMET case — the financial store's maintenance-restore vector, where refusal precedes any write — is labelled in §2.6.1 as a **proposed design property, not an executed RQ-3 pass** (revision 4): the design claims it by construction; no run has proven it. This design does not claim RQ-3 is resolved, does not ask for it to be read down silently, and records the choice where it belongs: §6, Atlas item 5 — a recorded requirements disposition, or the UNMET markings stand. The one availability consequence is stated openly: an anchor-unit outage blocks decisions and restores while it lasts (fail-closed by design); RQ-6 is satisfied because with the genuine latest state and a healthy anchor, verification passes and work proceeds.

## 5. What this does NOT fix

- **Fencing.** UNSOLVED and untouched (§2.7). The P-8 written disposition (accepted-open-risk or wait) is still required before INT-5 execution; this design is not that disposition, the Atlas review of revision 1 supplied none, and this revision does not discharge the activation prerequisite INT-4 names.
- **RQ-8.** A synthetic/offline pass still proves the pattern only. Activation-grade qualification still requires one run against the real provisioned target using the provider's actual backup/restore mechanism — including the step-14 anchor-custody attempt. This design gives that run something to prove; it is not the proof. Q-C and Q-D remain UNPROVEN until their §3 obligations land.
- **RB-2 beyond the PostgreSQL native-history surface.** The durable floor covers the PG adapter's terminal-history path — the composed production surface. File/object-adapter history surfaces were not examined for equivalent seams in this draft and are outside the claim until separately wired and reviewed.
- **Joint rollback of store and anchor together, and total custody compromise.** Outside INT-4's adversary model. Stated for the cross-witness explicitly (revision 3): the witness (§2.3.5) detects anchor-side rollback and the frontier detects store-side rollback, but an adversary who rolls back the database domain, the witness, *and* the anchor unit to the same older instant re-presents a fully consistent world — undetectable within this design. The provenance log and the optional owner-held notarization (Candidate C as complement) are detection aids for the store+anchor case, not a mechanism against it; an anchor-unit restore invalidates qualification (§2.6) rather than being silently survived. A principal holding both the provisioning/admin channel and the notarization channel is outside the model entirely (§2.8).
- **RQ-3 byte preservation at an already-attacked destination.** Not fixed — marked, not solved (§2.6.1, §3 Q-E): for the authorization store, `terminal_history`, the anchor unit itself, and the financial store under direct byte replacement, this design detects and refuses but does not preserve the genuine latest bytes once they have been replaced. Only a recorded requirements disposition (§6, Atlas item 5) or a different preservation mechanism (undesigned here) changes those markings; no later revision of this design should be read as promising one.
- **Owner-key restore custody (INT-5 P-6 / checklist C-1).** Unchanged: the shipped object adapter's `backupStore.get()` still refuses without server-held decryption, so store-restore rows remain BLOCKED / NOT QUALIFIED until that separate custody path exists. This design verifies anchors *around* the restore path; it does not make archive retrieval possible.
- **Availability during an anchor outage.** Fail-closed is the design's answer, not a problem it solves away: decisions and restores block until the anchor is reachable and verifiable.
- **INT-3 / INT-5 execution, provisioning, activation.** None is advanced by this document. The G-2 re-baseline (P-3), INT-3 evidence (P-1), and every other INT-5 predecessor stand exactly as the INT-5 spec records them, as corrected by its own review record (#755 comment 6449825208: P-2's revision decision is met) and by Atlas's later acceptance of record (#715 comment 6449977123: **the offline BR re-baseline is accepted-as-scoped — it is not still pending**, and that acceptance is not qualification). Revision 2's contrary statement is withdrawn.
