## Boundary

`public/forecast.js::reconcileCardPurchases` qualifies allocation parts through
one local predicate. A current transaction must have explicit `pending: false`.
When the producer's existing `savingsPostingEvidence` leaf is present, it must
also be `posted`. That leaf is emitted for every account by the current producer.
An older normalized row with explicit `pending: false` and no optional leaf
remains valid. Confirmed opening purchase carry retains its existing independent
compatibility path.

`Forecast.validateCardPaymentDecision` and `Forecast.cardPeriodMovements` consume
this existing reconciler. There is no second allocation calculator. Purchase
counting, the shared pending classifier, payment-leg qualification, physical
movements, cash/debt calculation, issuer satisfaction, and the private controller
and store are unchanged. Unqualified coverage and its dependent holds are
expected to change. Whole-Forecast equality is not claimed.

The fixture goes through the actual observation-to-live-plan producer. Twenty
posting variants are each tested with an $80 full allocation and a $40 partial
allocation plus $40 other payment purpose. Current main incorrectly accepts
36 unqualified cases. The repaired source passes all 40 cases; the four valid
posted/legacy controls remain accepted. Missing, null, string, numeric and object

Independent cents: an $80 purchase and $80 payment leave observed cash
`50000 - 8000 = 42000` cents and posted debt
`40000 + 8000 - 8000 = 40000` cents. For a pending purchase, posted debt is
`40000 - 8000 = 32000` cents with an 8000-cent pending authorization. These
amounts are literal fixture expectations, not values generated by Forecast.
Before/after physical card movements are compared separately from allocation
metadata. Every purchase stays counted at 8000 cents. A rejected allocation has
zero covered cents and 8000 remaining cents. Valid partial coverage has 4000
covered and 4000 remaining cents; valid full coverage has 8000 and zero.
